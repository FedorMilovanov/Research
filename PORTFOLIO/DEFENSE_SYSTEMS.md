# Системы защиты, проверки и аккуратность анализа

Аудит не «что построено», а «насколько этому можно верить»: защитные механизмы по слоям, качество проверок и точность собственных цифр.

**Метод.** 183 workflow-файла во всех девяти репозиториях прочитаны и просканированы по паттернам; полные клоны `mp3telegrambot` (11,4 МБ) и `video-channel-manager` (95 МБ) для пересчёта тестов и строк; GitHub API для PR и бэклога; точки защиты искались и в коде, и в документах.
**Ограничение, важное с самого начала:** состояние branch protection и rulesets через API недоступно (`403 Resource not accessible by integration`) — ровно то же, что `AuditRepo` фиксирует как `UNPROVEN` 29.10.2026. Поэтому защита ветвей в этом документе **не оценивается**.

## 1. Карта защиты по слоям

### Слой 1. Секреты и учётные данные

| Что есть | Где | Оценка |
|---|---|---|
| `SECURITY.md` с моделью секретов и приватным каналом сообщений | `mp3telegrambot`, `DeepMovieReview` | **2 из 9** — мало |
| Сканирование истории на секреты | `gitleaks` в `mp3telegrambot`, `trufflehog` в одном workflow | **1–2 из 9** |
| Конфиг gitleaks с осознанным allowlist | `mp3telegrambot/.gitleaks.toml` | образцовый |
| Правило «секреты только в `.env`, никогда в git» | `mp3telegrambot`, `video-channel-manager`, `Milovi_Cake` | в остальных неявно |
| Инструкция о локальных источниках учётных данных | `video-channel-manager/docs/operations/local-credential-sources.md` | хорошо |

Цитата из `.gitleaks.toml` — она стоит того, чтобы её процитировать целиком:

> «Allowlist не должен становиться дырой: здесь нет ни одного пути целиком (`tests/`, `docs/`), потому что настоящий токен чаще всего попадает в код именно в тесте — при отладке. Разрешены только конкретные образцы-заглушки».

Это уровень понимания, который обычно появляется после инцидента, а не из статьи.

`SECURITY.md` в `mp3telegrambot` тоже сделан по-взрослому: приватный advisory вместо публичного issue, таблица категорий секретов с указанием, где они живут, честная строка «проект личный, поэтому сроки — „как можно быстрее", без SLA».

**Пробел:** в семи репозиториях нет ни `SECURITY.md`, ни сканирования. Для портфолио это самая дешёвая правка с самым заметным эффектом.

### Слой 3. Цепочка поставки CI/CD — здесь лучший результат аудита

Проверены все 183 workflow-файла:

| Показатель | Значение | Комментарий |
|---|---|---|
| Действия, прибитые к полному 40-символьному SHA | **576 из 576** | ни одной ссылки на `@v3`, `@main`, `@master` |
| Workflow, объявляющие `permissions:` | **183 из 183** | нет ни одного с `write-all` |
| `persist-credentials: false` | 104 | токен не остаётся в `.git/config` после checkout |
| `concurrency:` | 141 | защита от параллельных дублей |
| `timeout-minutes` | 166 | нет висящих джобов |
| `pull_request_target` | 2 | оба — безопасный случай, см. ниже |
| `workflow_run` | 15 | постобработка после CI |

**Про `pull_request_target`.** Это классическая ловушка: если такой workflow чекаутит код из PR, злоумышленник получает токен с правами записи. Оба случая — `branch-cleanup.yml` в `Milovi_Cake` и `Milovi_School` — устроены правильно:

- нет `actions/checkout` вообще, значит код PR не исполняется;
- условие `github.event.pull_request.head.repo.full_name == github.repository` — форки отсечены;
- проверка префикса ветки (`audit/`, `ci/`, `tmp/`, `dependabot/`…) и отказ на `main`/`refs/`;
- значение ветки передаётся через `env`, а не подставляется в `run:` — инъекции нет;
- `timeout-minutes: 5`.

Единственное замечание: `permissions: contents: write` — шире, чем нужно для удаления одной ветки, но удаление ref без этого невозможно. Приемлемо; в идеале ограничивается ruleset'ом.

**Вывод по слою:** 576/576 пинов и 183/183 объявленных прав — это выше, чем у большинства коммерческих команд. Проверено пересчётом, а не взято из README.

### Слой 5. Операции с внешними системами

- Разделение состояний завершённости: реализация ≠ артефакт ≠ право на исполнение.
- Точная идентичность цели: `project_key` + `channel_id`/`community_id` + `owner_id`, «алиас не выбирает проект».
- Неизменяемая идентичность операции: SHA-256 медиа, digest очереди, стабильный ledger-key.
- `never_replay` для неопределённых состояний провайдера.
- Посткондиция после каждой записи, отдельно от HTTP-ответа.
- Append-only ledger с запретом перезаписи истории.
- Runbook'и, шаблон инцидента, postmortem с числом объектов (403 удаления, 2 879 инвентарь).
- Ограниченные повторы (`bounded polling`), осознанный отказ от «ещё немного подождать».

### Слой 6. Редакционно-правовые границы

- `AI_DO_NOT_TOUCH_GUARDRAILS.md` — файл-запрет на правку того, что агенту трогать нельзя.
- Правило «наличие записи не даёт прав на медиа» и 59 Reel-задач в состоянии `provider-inert`.
- Явное разделение «перевод/редактура — человек» и «генерация — модель».
- Отказ от републикации чужого видео без прав.

### Слой 7. Данные исследования

- Реестр authority: новый документ не становится источником истины автоматически.
- Классы источников (A1…D), `HOLD`-флаги, «неопределённость — состояние, а не ошибка».
- Явные маркеры `UNPROVEN` вместо умолчаний.
- Версионирование истины: `current-state.md` прямо пишет «этот раздел замещает раздел от 15 октября».

## 3. Что реально не защищено

1. **Сканирование секретов в 1 из 9 репозиториев.** Это самый большой разрыв: одна утёкшая строка в `.env.example` или тесте обесценивает всё остальное. Лечится включением GitHub secret scanning + push protection в настройках и добавлением gitleaks-джобы в общий шаблон.
2. **`SECURITY.md` в 2 из 9.** Ноль рублей, ноль времени, заметный сигнал зрелости.
3. **Нет `CODEOWNERS` в 4 репозиториях**, нет pre-commit нигде, кроме `mp3telegrambot`.
4. **Branch protection и rulesets не подтверждены.** Это не значит «нет» — это значит «не проверено». В портфолио так и надо писать.
5. **`gb-is-my-strength`: 77 гейтов, но ноль unit-тестов.** Структурные проверки не ловят логические ошибки; для контентного проекта это отчасти оправдано, но в интервью надо говорить именно так, а не «у меня всё покрыто тестами».
6. **`video-channel-manager` без единого тега и без `SECURITY.md`** при том, что это самый защищённый по логике проект.

## 4. Аккуратность анализа и сбора данных — измерение

Здесь я проверял не декларации, а воспроизводимость. Взял цифры из его документов и пересчитал по коду.

| Утверждение | Проверка | Результат |
|---|---|---|
| «919 модулей, 219 040 строк Python» (`video-channel-manager`) | полный клон, `find`+`wc -l` | **919 файлов, 219 040 строк** — совпало до строки |
| «936 модулей» (`mp3telegrambot`) | полный клон | **936** — совпало |
| «461 тест» (`video-channel-manager`) | полный клон | 461 **тестовый файл**, но **2 843 тестовые функции** |
| «4 487 тестов в прогоне» (`mp3telegrambot`) | полный клон | 4 141 `def test_` + параметризация ≈ 4 487 — сходится |
| «111 страниц» (`gb-is-my-strength`) | `ls-tree` | **111** `.astro` страниц — точно |
| «77 CI-гейтов» | `ls-tree` | **77** workflow — точно |
| «22 опубликовано / 38 в очереди» | ledger-записи | последовательность 18–22 → сообщения 1570–1576, сходится |

**Главная находка:** цифры не завышены — они **занижены из-за подписи**. «461 тест» на самом деле 2 843 теста; ошибка не в подсчёте, а в единице измерения. Это редкий и симпатичный тип ошибки: человек из скромности называет тестами файлы.

**Вторая находка — дисциплина доказательств.** В `AuditRepo` и `current-state.md` есть практики, которые обычно отсутствуют даже в корпоративных аудитах:

- `exact anchor` — каждая запись привязана к SHA;
- `UNPROVEN` — прямое признание неизвестного вместо умолчания;
- «does not pretend to be a new independent Render API session» — отказ выдавать пересказ за проверку;
- append-only ledger с явным правилом «новая запись не возвращает задачу в работу»;
- «этот раздел замещает предыдущий» — версионирование истины;
- различение «данные получены» и «данные актуальны» (freshness limitation).

Это и есть ответ на вопрос «насколько аккуратен сбор данных»: **аккуратность обеспечивается не вниманием, а форматом записи**. Когда каждая цифра обязана иметь якорь, класс сигнала и пометку о свежести, соврать трудно.

## 6. Оценка в одну страницу

**Что защищено хорошо.** Цепочка поставки CI (576/576 пинов, 183/183 прав, отсутствие `write-all`, безопасный `pull_request_target`), работа с зависимостями (политика, группировка, хэш-локи, аудит), операционная защита от неопределённости (no-replay, посткондиции, точная идентичность), доказательная дисциплина документов (якоря, `UNPROVEN`, версионирование истины), редакционно-правовые границы.

**Что защищено слабо.** Секреты: сканирование в одном репозитории из девяти, `SECURITY.md` в двух. Нет единого шаблона workflow для новых репозиториев — из-за этого практика расползается неравномерно. Branch protection не подтверждён.

**Три действия с максимальной отдачей:**

1. `SECURITY.md` + secret scanning + push protection — во все девять репозиториев (вечер работы, закрывает главный разрыв).
2. Общий reusable workflow «security baseline» (gitleaks + `pip-audit`/`npm audit` + пины) — подключается одной строкой в новые проекты.
3. Зафиксировать branch protection/rulesets документально — со скриншотом и датой, вместо `UNPROVEN`.

**Формулировка для интервью:**

> «У меня 183 workflow, и во всех 576 внешних действий прибиты к полному SHA, ни одного `write-all`, ни одного небезопасного `pull_request_target`. Зависимости обновляются ботом, но мержатся только через обязательный гейт с аудитом. Секреты сканируются в одном репозитории из девяти — это мой известный разрыв, и он закрывается шаблоном, а не героизмом».
