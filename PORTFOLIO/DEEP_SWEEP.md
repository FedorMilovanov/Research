# Глубокий проход: то, что не попало в первые четыре раунда

Пятый раунд. Смотрел не «что написано», а «как это работает на практике»: пропускную способность PR, гигиену бэклога, ритм работы, объём проверок, релизы и операционные документы, которые раньше только перечислял.

**Источники:** 17 836 коммитов в десяти клонах, GitHub API (`search/issues`, `repos`), 391 отчёт верификации в `AuditRepo`, `CLOSURE_LEDGER.md` по 8 проектам, `docs/operations/current-state.md`, `AI_DO_NOT_TOUCH_GUARDRAILS.md`.
**Срез:** 1 ноября 2026.

## 2. Ритм: как это делалось физически

**Часы.** Коммиты владельца (14 220 штук):

| Интервал (MSK) | Коммитов | Доля |
|---|---|---|
| 22:00–02:00 | 3 898 | **27 %** |
| 02:00–06:00 | 1 778 | 13 % |
| 12:00–18:00 | 3 969 | 28 % |
| 06:00–12:00 | 1 115 | 8 % |

31 % коммитов — между полуночью и шестью утра. Таймзона в метаданных — `+0300` у 12 767 коммитов, `+0000` у 1 453 (агентские и CI). Оговорка: часть ночных коммитов могла быть создана автоматикой под его идентичностью, поэтому «работал ночами» — это вывод из метаданных, а не из его слов.

**Дни недели.** Понедельник — 3 327, суббота — 2 764, воскресенье — 2 383. Выходные — **29 %** всей активности. Работа шла непрерывно, без «спринтов по будням».

**Перерывы и пики.** Максимальный перерыв между днями с коммитами — 18 дней, и только в `gb-is-my-strength`; в остальных репозиториях — 0–1 день. Самые плотные сутки: `mp3telegrambot` — 342 коммита (29.07), `bible-bot` — 323 (10.08), `video-channel-manager` — 311 (25.07), `TheLegendaryPoet` — 244 (03.08), `gb-is-my-strength` — 167 (12.09).

Это картина не «раз в неделю собрался», а ежедневной операции: в среднем **64,6 коммита в день** за 276 дней.

## 6. Операционная зрелость: цитаты, которые стоят дороже цифр

Из `video-channel-manager/docs/operations/current-state.md` (21.10.2026):

> «Repository implementation, artifact production and provider rollout are separate completion states. Implementation completion does not itself authorize execution».

> «Credentials authenticate; exact project identity, target binding, immutable operation/release identity, durable state and fresh explicit execution authority select the operation».

> «An ambiguous provider effect remains blocking unless exact read-only reconciliation or a narrowly bound no-replay disposition resolves it».

Там же — состояние производства: **22 опубликовано / 38 в очереди**, следующий номер публикации 23, digest очереди `sha256:8d7dfd23…`, durable-сообщения 1570–1576, активационная граница 17/43. И запись о том, что при неверной переменной `LORDCHRIST_APPROVED_QUEUE_DIGEST` расписание «fail closed на этом гейте».

Из `CLOSURE_LEDGER` (`mp3telegrambot`, 29.10.2026):

> «wholesale rollback rejected; three verified engineering roots and one narrowed live-canary residual remain».

> «dependency audit, CodeQL and full-history gitleaks green; … Bandit candidates manually source-reviewed; no production `shell=True`, unsafe extraction or unbounded dynamic SQL identifier found».

Из `Milovi_Cake/AI_DO_NOT_TOUCH_GUARDRAILS.md` — файл, запрещающий агенту трогать то, что нельзя (отдельный жанр документации, который почти никто не пишет).

Из `bible-bot` ledger — контроль-плоскость деплоя: `autoDeployTrigger=checksPass`, `healthCheckPath=/production/ready`, четыре readiness-эндпоинта зелёные.

**Почему это важно для портфолио.** Это не рассказ «я аккуратный». Это документы, где видно: разделение состояний завершённости, неизменяемая идентичность операции, отказ от повторной записи при неопределённости, проверка зависимостей с известными уязвимостями (Pillow 12.3.0 → 13.0.0: 24 уязвимости), пиннинг GitHub Actions по полному SHA с тестом.

## 7. Удаление как практика

947 коммитов (5,3 %) используют глаголы сокращения: `remove` — 605, `retire` — 212, `delete` — 126, `archive` — 113, `prune` — 3. Против 33 упоминаний `revert` (0,18 %).

Это важное соотношение: **удаляют в 29 раз чаще, чем откатывают**. То есть объём сокращается осознанно, а не откатывается после аварий.

## 8. Честные ограничения этого прохода

- **CI-статистика непригодна.** Эндпоинт возвращает `total_count`, зажатый на 2 500; по нескольким репозиториям success и failure оба равны 2 500. Долю успешных прогонов по API не получить — нужен экспорт из биллинга или выгрузка runs постранично.
- **Гипербола невозможна:** `4 487` тестов — это значение из ledger'а от 29.10.2026, а не сегодняшний прогон.
- **Ночная активность** может частично принадлежать автоматике под его идентичностью.
- **Ветвления и защита ветвей** остаются непроверенными: `AuditRepo` прямо фиксирует «branch-protection state not obtainable by integration and remains UNPROVEN».
- **Отчёты `AuditRepo`** — 391 файл с именем `REPORT.md` (399 с вариантами имени); прочитаны выборочно (ledger'ы, матрицы, 6–8 отчётов), не все.

## 9. Что добавить в портфолио (готовые формулировки)

1. **Пропускная способность.** «3 834 пулл-реквеста, из них смержено 2 876 (75 %), при 39 открытых issue на девять репозиториев».
2. **Масштаб проверок.** «4 487 тестов в одном прогоне, 391 отчёт верификации, 166/166 URL, проверенных в Search Console, 69/69 closed-unmerged PR, разобранных до конца».
3. **Ритм.** «276 дней ежедневной работы, 64,6 коммита в день, 29 % активности в выходные; максимальный перерыв — 18 дней».
4. **Удаление.** «947 коммитов сокращают объём против 33 откатов: система уменьшается осознанно, а не чинится после аварий».
5. **Операционная зрелость.** «Разделение состояний завершённости: реализация не равна артефакту, артефакт не равен правам на исполнение; неопределённый эффект провайдера блокирует повтор до точной сверки».
6. **Версионирование.** «143 тега в `gb-is-my-strength`, 88 в `TheLegendaryPoet`; у сервисных репозиториев версий нет — и это следующий шаг».

**Чего не говорить:** «мой CI успешен в N % случаев» — этих данных нет, и любой, кто откроет API, это увидит.
