# Как делать PR в чужие проекты

Практическое руководство под твой случай: не «стать контрибьютором опенсорса», а сделать 2–3 полезных PR, которые (а) действительно нужны проекту, (б) не отнимут месяц, (в) появятся в профиле как «Contributed to».

**Честная рамка.** Три PR не принесут звёзд и трафика. Они дают другое: строку в профиле, опыт работы в чужом процессе (ревью, стиль, CI), внешние ссылки и материал для разговора на интервью. Это инвестиция в credibility, а не в дистрибуцию.

---

## 1. Как устроена механика

У тебя нет прав записи в чужой репозиторий. Поэтому используется форк-модель:

```
чужой репозиторий (upstream)  ← PR ←  твой форк (origin)  ←  твоя локальная копия
```

1. **Форк** — кнопка `Fork` на странице проекта. Появляется `github.com/Ты/проект`.
2. **Клон своего форка** локально, `upstream` добавляется как второй remote.
3. **Ветка** с осмысленным именем, один коммит (или несколько логичных).
4. **Push** в свой форк.
5. **PR** из ветки форка в `main` апстрима. GitHub предложит кнопку сразу после push.
6. **Ревью**: мейнтейнер просит правки → коммитишь в ту же ветку → PR обновляется сам.
7. **Merge** делает мейнтейнер (иногда просит squash).

Ничего из этого не требует особых прав. Всё, что нужно, — аккаунт GitHub, который у тебя есть.

## 2. Пошагово

### Шаг 1. Найти повод

Три источника, по убыванию качества:

**а) Свои грабли.** Лучший источник — то, на что ты уже наткнулся. У тебя в проектах есть реальные интеграции: браузерный ONNX-порт TTS, Pagefind на русском, Astro с мультиязычными маршрутами, Telegram Mini App на MongoDB, Playwright на сайте без сборки. Каждая неочевидная деталь, которую ты выяснил сам, — готовый вклад в документацию.

**б) Поиск по меткам.** В строке поиска GitHub:

```
is:issue is:open label:"good first issue" language:TypeScript
is:issue is:open label:documentation no:assignee sort:created-desc
is:issue is:open label:i18n "Russian"
```

Фильтр `no:assignee` важен: иначе возьмёшь то, что уже делает кто-то другой.

**в) Свой баг-репорт.** Если нашёл дефект — сначала issue с воспроизведением, потом PR. Часто мейнтейнер сам говорит «присылай», и тогда PR почти гарантированно примут.

### Шаг 2. Прочитать правила проекта

В корне ищи: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `.github/PULL_REQUEST_TEMPLATE.md`, `docs/contributing*`. Там написано: как оформлять коммиты, нужен ли `Signed-off-by` (DCO), есть ли CLA, какой стиль и какие проверки.

Если `CONTRIBUTING.md` нет и проект маленький — просто пиши по-человечески и маленькими диффами.

### Шаг 3. Заявить о намерении

В issue: «I'd like to take this. My plan: …». Это стоит 2 минуты и спасает от ситуации «сделал, а уже сделано другим».

Исключение: опечатка в документации — можно сразу PR, без церемоний.

### Шаг 4. Форк, клон, upstream

```bash
# 1. Форк через веб-интерфейс, затем:
git clone git@github.com:ТВОЙ_ЛОГИН/проект.git
cd проект

# 2. Добавить апстрим
git remote add upstream https://github.com/ВЛАДЕЛЕЦ/проект.git
git remote -v

# 3. Свежая база
git fetch upstream
git checkout -b docs/browser-onnx-example upstream/main
```

Правило: ветку всегда от свежего `upstream/main`, а не от своего старого форка.

### Шаг 5. Сделать изменение

Требования, которые чаще всего нарушают новички:

- **Один PR — одна мысль.** Не смешивай опечатку, рефакторинг и новую функцию.
- **Не переформатируй файл.** Если поправил строку — в диффе должна быть одна строка. Переформатирование всего файла мейнтейнер отклонит.
- **Попадай в стиль.** Отступы, кавычки, длина строк — как в соседнем коде, а не как тебе нравится.
- **Минимум кода — максимум пользы.** Документация, пример, тест принимаются легче, чем «улучшение архитектуры».

### Шаг 6. Коммит

```bash
git add путь/к/файлу
git commit -s -m "docs: add browser ONNX usage example"
```

Флаг `-s` добавляет `Signed-off-by` — этого требуют проекты с DCO (например, многие проекты CNCF). Если проект требует, а ты забыл — попросят переделать.

Сообщение — в стиле проекта. Если в истории `fix: ...` — пиши так же; если «Fix typo in README» — пиши так.

### Шаг 7. Push и PR

```bash
git push -u origin docs/browser-onnx-example
```

Дальше GitHub покажет ссылку «Compare & pull request». Важно: **base repository** должен быть апстримом, **base branch** — `main` (или `master`), **head** — твоя ветка в форке.

Тело PR:

```markdown
## What
Adds a browser/ONNX usage example for vosk-tts, covering model loading,
Cache API usage and the 16 kHz input requirement.

## Why
Integrating the library in a static Astro site required figuring this out
from source code; the pitfalls cost me a day. Documenting them saves the
next integrator the same day.

Fixes #123
```

Строка `Fixes #123` автоматически закроет issue после мержа.

### Шаг 8. Ревью

- Ответили «please change X» — правь в той же ветке, новый коммит, push. PR обновится сам.
- Просят squash — `git rebase -i upstream/main` и `git push --force-with-lease`.
- Просят тест — добавь тест, даже если кажется избыточным.
- Молчат 7–14 дней — одно вежливое напоминание в комментарии. Не больше.
- Отказали — это норма. Спроси причину, не спорь. Отказ ничего не значит для репутации; агрессия в ревью — значит.

### Шаг 9. После мержа

```bash
git checkout main
git fetch upstream
git reset --hard upstream/main
git push origin main
git branch -d docs/browser-onnx-example
```

Удалить ветку в форке можно кнопкой на GitHub. Держать форк в актуальном состоянии необязательно, но удобно.

## 3. Десять правил, которые решают исход

1. **Маленький дифф.** 5–50 строк — идеально. 500 строк новичка почти всегда отклоняют.
2. **Сначала issue, потом PR** — если это не опечатка.
3. **Не трогай чужой код без причины.** Каждая изменённая строка должна быть объяснима.
4. **Не спорь о вкусе.** Вкус мейнтейнера — закон в его репозитории.
5. **Добавляй тест, если есть инфраструктура тестов.** Тест без инфраструктуры — не добавляй.
6. **Не подписывай CLA от чужого имени.** Если проект требует CLA, читай его сам; агент не имеет права соглашаться за тебя.
7. **Раскрывай помощь ИИ, если спросят.** «Drafted with an AI assistant, reviewed and tested by me» — нормальная формулировка в 2026.
8. **Не отправляй сгенерированный текст без вычитки.** Именно на этом горят «AI-slop PR»: вода, ложные утверждения, выдуманные API.
9. **Уважай лицензию.** Вклад в GPL-проект не означает, что код можно копировать в свои MIT-репозитории.
10. **Один PR — один репозиторий.** Массовые одновременные PR в десять проектов выглядят как накрутка.

## 4. Что предлагать именно тебе

У тебя редкая позиция: ты не автор библиотек, но **интегратор**, который довёл чужие инструменты до продакшна. Это самый дефицитный вклад — «я реально это применил, вот что сломалось».

| Проект | Повод из твоего опыта | Что предложить | Сложность | Шанс принятия |
|---|---|---|---|---|
| `alphacep/vosk-tts` | браузерный ONNX-порт, кэш модели, частота 16 кГц, слой ударений | `examples/browser/README.md` с подводными камнями + ссылка на живой сайт | низкая | высокий |
| `Pagefind` | русский поиск на статическом сайте: морфология, подсветка, размер индекса | страница документации «Russian sites» или issue с воспроизведением | низкая | средний |
| `withastro/astro` | мультиязычные маршруты, sitemap, JSON-LD на 111 страницах | пример в `examples/` или правка документации по i18n | средняя | средний |
| `python-telegram-bot` / `aiogram` | Mini App + MongoDB + проверка `initData` | документация по проверке подписи `initData` на сервере | средняя | высокий |
| `microsoft/playwright` | PWA без сборки, офлайн-режим, Lighthouse-регрессии | issue с воспроизведением или пример в docs | средняя | средний |
| `yt-dlp` | снимки канала, экстракторы, нестабильные поля | баг-репорт с точным воспроизведением (PR — только если готов к Python-экстракторам) | высокая | зависит |

**С чего начать конкретно:** `vosk-tts`, браузерный пример. Ты единственный, кто это сделал на практике, а в проекте такого примера, судя по структуре, нет. Это вклад, который не стыдно и полезно.

**Как проверить, что повод реальный:** открой исходники, найди место, где ты споткнулся, и посмотри, описано ли это. Если нет — это и есть твой PR.

## 5. Как делегировать это агенту

| Делает агент | Делает человек |
|---|---|
| ищет подходящие issue по меткам и языку | выбирает, за что браться |
| читает `CONTRIBUTING.md` и пересказывает правила | подтверждает, что правила понятны |
| собирает форк, ветку, патч, прогоняет тесты проекта | проверяет дифф построчно |
| пишет черновик issue и тела PR | вычитывает, убирает воду и выдуманные утверждения |
| готовит ответ на замечания ревью | отправляет ответ, подписывает CLA, несёт ответственность |

**Чего агент не делает никогда:** не нажимает «Submit» в чужом репозитории без твоей вычитки, не подписывает CLA, не отвечает мейнтейнеру от твоего имени, не отправляет PR в десять проектов сразу.

Промт:

```text
Найди в проекте <owner/repo> три места, где документация не покрывает
<конкретный сценарий: браузерный ONNX / русский поиск / Mini App initData>.
Прочитай CONTRIBUTING.md и .github/PULL_REQUEST_TEMPLATE.md, перескажи правила.
Предложи ОДИН минимальный дифф (docs или пример), не меняя код без необходимости.
Подготовь: ветку от upstream/main, коммит с -s, черновик issue и тела PR на английском.
Ничего не отправляй. Покажи дифф и тексты мне.
```

## 6. Чего не делать

| Так | Почему |
|---|---|
| Массовые PR «fix typo» по десяткам репозиториев | выглядит как накрутка профиля, мейнтейнеры банят |
| «Улучшил архитектуру» без обсуждения | почти гарантированный отказ и испорченное впечатление |
| Автоматические PR от бота | многие проекты закрывают такие без рассмотрения |
| PR в заброшенный репозиторий | годы без ответа, в профиле — мёртвый вклад |
| Копирование кода из чужого проекта в свой | лицензионная проблема, а не вклад |
| Спор в ревью | репутационный вред больше, чем польза от мержа |
| Отправка сгенерированного текста без проверки | «AI slop» — сейчас главная причина отказа новичкам |

## 7. Ожидания

| Что | Реалистично |
|---|---|
| Время на первый PR | 3–6 часов, включая чтение правил и прогон тестов |
| Ответ мейнтейнера | 2–14 дней, иногда месяц |
| Доля принятых PR у новичка | 30–50 %; отказ — обычная часть процесса |
| Что появится в профиле | «Contributed to owner/repo» и ссылка на PR |
| Что это даст для поиска | почти ничего напрямую; немного — через внешние ссылки |

Три PR — это не «стать известным». Это доказательство, что ты умеешь работать в чужом процессе. Для найма и для переговоров это весомее, чем ещё один собственный репозиторий.

## 8. Чек-лист первого PR

- [ ] Выбран проект, которым реально пользовался.
- [ ] Прочитаны `CONTRIBUTING.md` и шаблон PR.
- [ ] Проверено, что issue не занят (`no:assignee`) и не решён.
- [ ] Написан комментарий «I'd like to take this».
- [ ] Форк, ветка от `upstream/main`, один смысловой коммит с `-s`.
- [ ] Дифф меньше 50 строк, без переформатирования.
- [ ] Тесты/линтеры проекта прогнаны локально.
- [ ] Тело PR: что, зачем, `Fixes #N`.
- [ ] После отправки — никаких напоминаний раньше седьмого дня.
