# Три набора данных `official core 59` воспроизводимы по коммиту (2026-11-18)

**Роль:** `DERIVED_READ_ONLY_NOT_AUTHORITY`. Квитанция про байты, не про права.

**Вопрос, на который отвечает документ.** Документ статуса от 2026-07-30 фиксирует: три
набора данных (STEPBible, `morphhb`, SBLGNT) отчёт объявил скачанными и проверенными, но в
архиве на Drive их нет. Единственный живой кандидат на копию — артефакт CI
`ephemeral-official-core-acquisition-59-v2` на 123 193 373 Б, истекающий 2026-11-24. Отсюда
вопрос: **что будет, когда артефакт исчезнет** — доказательство пропадёт или его можно
восстановить?

**Ответ: восстановить можно, и без артефакта.** Байты детерминированно собираются с
`codeload.github.com` по зафиксированному коммиту, и все три размера совпали с записанными
байт в байт.

## 1. Что проверено

Скачивание в `/tmp` песочницы по шаблону
`https://codeload.github.com/{owner}/{repo}/zip/{commit}`, затем сравнение размера с
документом статуса и локальный `sha256`. В репозитории и на Drive ничего не менялось.

|---|---|---:|---:|:--:|---|
| STEPBible Data | `STEPBible/STEPBible-Data` @ `b86d26cdb1f51729e73b5b4eb7f7ccadc5dfba39` | 100 920 275 | 100 920 275 | да | `6845fa96…5d35182df0` |
| Open Scriptures `morphhb` | `openscriptures/morphhb` @ `3d15126fb1ef74867fc1434be1942e837932691f` | 20 870 584 | 20 870 584 | да | `f56c1507…5b5d177b4c7` |
| Faithlife SBLGNT | `Faithlife/SBLGNT` @ `c4d241a9c1c479a55b989ba35a4976c1d0b8052c` | 1 414 688 | 1 414 688 | да | `4fc2659c…f05dae530e4c0f` |
| **Итого** | | **123 205 547** | **123 205 547** | **3/3** | |

Все три коммита на 2026-11-18 резолвятся через `api.github.com`, то есть архивы доступны.
Проверка воспроизводимости: повторное скачивание того же URL даёт тот же размер; коммиты
неизменяемы, пока апстрим не перезапишет историю.

## 2. Что это меняет в оценке риска

Прежняя формулировка — «единственная копия исчезает 24 ноября» — была неверной. Точная:

- **артефакт CI не нужен для восстановления.** Его содержимое так и не проверено (скачивание
  из песочницы блокируется: `gh api` уводит на `productionresultssa5.blob.core.windows.net`),
  но это больше не важно: байты берутся из апстрима по коммиту;
- **дата 2026-11-24 перестаёт быть дедлайном хранения.** Она остаётся дедлайном только для
  удобства — «забрать то, что уже лежит под рукой», а не «спасти единственную копию»;
- **впервые появились SHA-256** трёх наборов. До этого в репозитории были только размеры и
  коммиты, то есть проверять было нечего.

## 3. Чего это не доказывает

- **Права.** Воспроизводимость архива — не разрешение на использование. В очереди кандидатов
  v1 права записаны как «dataset-specific; verify each subdataset» для STEPBible,
  «WLC text public domain; morphology CC BY 4.0» для `morphhb`, «CC BY 4.0» для SBLGNT. Это
  заявленные лицензии репозиториев, а не решение владельца корпуса.
- **Содержимое.** Архивы не распаковывались и не читались: проверен носитель, а не текст.
- **Полноту.** Совпадение размера с записанным в 2026-07-30 — это совпадение с *тем* отчётом.
  Если сам отчёт ошибался в природе объекта (например, для STEPBible «dataset-specific» —
  это набор подкаталогов с разными условиями), квитанция эту ошибку не поймает.

## 4. Что остаётся сделать — и это уже не про хранение

1. Решить права по трём наборам отдельно, по подкаталогам STEPBible, а не «по репозиторию».
   Что именно заявлено внутри архива — §5.
2. Если решение положительное — приобрести на Drive с квитанцией (Drive ID + размер + SHA-256
   из таблицы выше) и только тогда писать в реестре, что наборы сохранены.
3. Артефакт 2026-11-24 не трогать специально: он больше не единственный носитель.

## 5. Права по подкаталогам: что заявляет сам архив

Раздел добавлен позже в тот же день. Задача из §4.1 («verify each subdataset») перестала быть
неопределённой, как только архив распакован: имён и одного README достаточно, чтобы перечислить
подкаталоги и увидеть, где условия расходятся с базовым CC BY 4.0.

Закрепление входа то же, что в §1: коммит `b86d26cd…`, 100 920 275 Б, SHA-256
`6845fa96…5d35182df0` — скрипт сверяет и размер, и хеш, и при расхождении не пишет ничего.

README начинается словами «STEPBible Data Repository **CC BY 4.0**», требует атрибуции
«STEP Bible» со ссылкой на www.STEPBible.org и разрешает изменения с обязанностью их
записывать. То есть базовая лицензия действительно одна, но два подкаталога из семи из неё
выпадают:

- **`Tagged-Bibles/TTESV` — `CC BY-NC`**, 4 434 578 Б: разметка ESV. Некоммерческая лицензия
  и чужой текст (ESV © Crossway) — ограничение на использование, причём сильнее остальных
  наборов. Для проекта это единственный NC-объект в трёх наборах.
- **`Tagged-Bibles/Arabic Bibles` — `CC BY-SA`**, 113 981 535 Б, 70 файлов с токеном:
  share-alike, то есть производные обязаны распространяться на тех же условиях. Внутри
  остаются 6 файлов без токена (4 `.docx` «SVD Tagging Documents» на 8 413 965 Б и два
  placeholder'а по 1 Б) — по ним условия не заявлены ни именем, ни README.
- **`Lexicons`**: README оговаривает, что «much of the data is based on other publically
  licenced sources». TFLSJ — полный LSJ, TBESG — на основе Abbott-Smith. CC BY 4.0 заявлен на
  форматирование и разметку; права на исходные словари этим не подтверждены.

Границы этого раздела те же, что и у §3: лицензия в имени файла — утверждение
распространителя, а не решение владельца; содержимое файлов не читалось; ни один HOLD не
снят. Практический вывод один — вопрос «какие права у STEPBible» сводится к вопросу «нужен ли
нам ESV-разметка (NC) и арабские разметки (SA)», потому что остальные пять подкаталогов
заявлены как CC BY 4.0 с атрибуцией.

Воспроизведение: `curl -sSLo /tmp/stepbible.zip <url из §1>` затем
`python3 scripts/stepbible_subdataset_terms.py --zip /tmp/stepbible.zip --write`;
гейт — `python3 scripts/stepbible_subdataset_terms.py --check` (без сети и без архива).
