# Песочница поднялась shallow-клоном: симптом, лечение, чего не делать

**Дата:** 2026-11-18
**Роль:** рабочая записка о среде, `NOT_AUTHORITY` в отношении корпуса
**Зачем:** четырежды за сессию рабочее дерево выглядело так, будто вся работа ветки не закоммичена, а гейт целостности падал на `commitTimeChecks`. Причина одна и та же, лечение — четыре команды; записано, чтобы пятый раз не диагностировать с нуля.

## 1. Симптом

- `python3 scripts/validate_atonement_corpus_integrity.py` → **FAIL**, единственная причина:
  `commitTimeChecks: ни одна из 16 записей не сверена (git не видит ни одного коммита) — проверка, которая ничего не сверяет, не имеет права называться PASS; обычная причина — shallow-клон или отсутствие .git`;
- `git log --oneline -1` показывает базовый коммит, хотя ветка ушла вперёд на десять коммитов;
- `git status` показывает десятки «изменений» в файлах, которых в этом ходе никто не трогал, — это содержимое ветки, лёгшее поверх базы;
- `git rev-parse --is-shallow-repository` → `true`, `git rev-list --count HEAD` → `1`.

Случается это не только между ходами: два из четырёх раз песочница откатилась **между двумя вызовами внутри одного хода** — файлы успевали прожить несколько минут в правильном состоянии, а следующий вызов видел базу. Признак тот же, поэтому различать эти случаи не нужно; важно не приниматься за работу, не проверив `rev-parse --is-shallow-repository`.

## 2. Диагноз

Файлы на диске — **состояние верхушки ветки** (последний ход), а `.git` — свежий клон глубины 1 на базовом коммите. Поэтому всё выглядит как «незакоммиченная работа», хотя коммиты целы: они лежат на `origin`. Ничего не потеряно ни разу; теряется только время на диагностику.

## 3. Лечение

```bash
git diff > /tmp/workspace-before-reset.patch      # страховка: 7 тысяч строк дешевле, чем сомнение
git fetch --unshallow origin                      # история: 3698 коммитов вместо одного
git fetch origin arena/<ветка>                    # верхушка ветки в origin/<ветка>
git reset --mixed origin/arena/<ветка>            # указатель на верхушку, рабочее дерево НЕ трогается
```

Затем проверить:

```bash
git rev-parse --is-shallow-repository     # false
git rev-list --count HEAD                 # тысячи, а не 1
git status --porcelain                    # только то, что действительно правил в этом ходе
python3 -B scripts/validate_atonement_corpus_integrity.py   # PASS
```

`--mixed` (или `--soft`) обязателен именно потому, что он двигает указатель и индекс, но не файлы: содержимое верхушки на диске и содержимое верхушки в git совпадают, поэтому после сброса в `git status` остаются только настоящие правки хода.

Процедура идемпотентна: повторный прогон на здоровом дереве ничего не меняет (`fetch --unshallow` на полном клоне отвечает «--unshallow on a complete repository does not make sense», `reset --mixed` на ту же верхушку — no-op). Поэтому её дешевле выполнить, чем выяснять, сломано ли дерево.

## 4. Чего не делать

- **`git reset --hard` и `git checkout -f`** — они уничтожат ровно то, что ещё не закоммичено; в этой сессии `reset --hard` уже однажды принимали за лечение базы, и это была ошибка.
- **`git add -A` и коммит «всего дерева»** — получится дубль ветки: сорок коммитов в одном, и настоящая история правок исчезнет.
- **верить списку «изменённых» файлов** — в этом состоянии он описывает разницу между базой и верхушкой, а не работу текущего хода.
- **считать FAIL гейта содержательным** — пока `rev-list --count HEAD` равен единице, гейт говорит о клоне, а не о корпусе.

## 5. Почему гейт прав, а не сломан

`commitTimeChecks` сверяет записанные в реестре времена коммитов с `git log`. В мелком клоне половина этих коммитов недоступна, сверять нечего — и проверка честно отказывается называть себя PASS. Это то же правило, что и везде в этом репозитории: «ноль совпадений» не равно «всё совпало». Поэтому лечение — восстановить историю, а не отключить проверку.
